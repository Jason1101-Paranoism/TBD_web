> 立於 2026-08-30。適用 56 份模板的每一輪審閱與說明書輪調。
> 相關決策：**D-008**（事實來源）、**D-013**（凍結後才建 Sheet）、**D-014**（§07a 不做核取方塊）、
> **D-015**（審閱迴圈要繞回 repo）。
>
> **這份是正本。** Drive 上有一份給非工程成員看的唯讀鏡像，改流程一律改這裡再重新產生那份：
> [模板審閱流程（唯讀鏡像）](https://docs.google.com/document/d/19ToAsj70fXPhwpo1h5zrRQaoi4DjUgqGNSWtfcX-7Vo/edit)

「審閱中」目前 owner 是 `stream.education.edu`；「工具銷售」是 `tbd.consulting.studio`。
工作副本的擁有權無所謂（用完即丟），出貨副本的擁有權要在建檔前確定（見第六節）。
新成員要加入審閱時，把「審閱中」分享給他即可，不要分享「工具銷售」。

這份要解的是一個具體問題：**審閱產出一直在 Drive，repo 看不到。**
所以進度只能靠 `progress/overlay.json` 手工維護，
而「這批審完了沒」這種問題沒有任何機器可以回答。

## 一、唯一的方向

```
   CSV（repo，正本）  ──▶  正式站（審閱者的入口）  ──▶  Drive「審閱中」（審閱者放的新版本）
        ▲                                                        │
        └────────────────  收斂者匯出 CSV 走 PR  ◀───────────────┘
```

**審閱者的入口是網站連結，不是 repo、也不是 Drive 上的舊副本。**
他們從正式站看當次的檔案，把修正後的新版本放進「審閱中」資料夾。

**永遠不要把 Drive 上那份當成定案。**
`audit-templates.mjs` 與 `npm run verify` 都是對著磁碟上的 CSV 驗的——
Drive 一旦成為正本，這兩道閘門立刻變瞎（D-008）。

審閱者可以、也應該直接改內容，那比留言快得多。
關鍵不是「不准改」，是**改完要繞回 CSV**，否則那份修改等於沒發生。

## 二、兩個資料夾，永不混用

| | 審閱中 | 工具銷售 |
|---|---|---|
| 放什麼 | 審閱者放上來的修正版本 | 出貨用的正式副本 |
| 何時建 | 隨時，該審就建空資料夾 | **該批凍結後才建**（D-013）|
| 壽命 | 用完即丟 | 長期，連結會發給買家 |
| 誰能改 | 該輪的審閱者 | 唯讀 |

**「工具銷售」資料夾裡永遠不會出現工作中的檔案。** 這是這兩個資料夾唯一的存在理由。

## 三、命名規則

### Drive 端（可以分岔，而且應該分岔）

```
{slug}__B{批次}-r{輪次}-{審閱者}-{YYYYMMDD}

grad-engineering-lab-compare__B1-r2-CL-20260901
grad-agriculture-oral-checklist__B3-r1-YY-20260905
```

四件事一眼看得出來：**這是哪一份、第幾批、第幾輪、誰改的、什麼時候**。
輪次從 r1 開始；同一份被退回重改就進 r2。

### repo 端（不可以分岔）

**檔名永遠是 `{slug}.csv`，不加 `_v2`、不加日期、不加人名。**

輪次與審閱者的資訊活在**分支名與 commit** 裡：

```
分支    review/B1-CL-20260901
commit  B1 r2 比較表審閱（CL）：七份的 shortlist 定位補上分層依據
```

理由：磁碟上一旦出現 `xxx_v2.csv`，`audit-templates.mjs` 就得決定要驗哪一個——
那正是 D-008 要擋的東西。**Drive 可以有分岔的名字，repo 不行。**

## 四、一輪審閱

| # | 誰 | 做什麼 |
|---|---|---|
| 1 | 收斂者 | 在 `審閱中/` 建該輪的空資料夾，把**該輪要看的網站連結**發給審閱者（正式站，不是 repo 路徑）|
| 2 | 審閱者 | 從網站連結看檔，**把修正後的新版本放進該輪資料夾**，依上面的命名。**只改自己被指派的那幾份**（輪調規則：審閱者與說明書撰寫者永不同人）|
| 3 | 審閱者 | 放完在該輪資料夾的紀錄檔上標「完成」，不必另外回報 |
| 4 | 收斂者 | 把改動匯出成 CSV，**覆蓋同一個 slug**，開分支送 PR |
| 5 | — | 閘門：`node scripts/audit-templates.mjs` → `npm run build` → `npm run verify` |
| 6 | 收斂者 | `docs/` 補一份逐項查證的 checklist，`docs/WORKLOG.md` 補一則 |
| 7 | 收斂者 | 更新 `progress/overlay.json` 的審閱／說明書狀態，重跑 `progress/build-progress.mjs` |
| 8 | 收斂者 | 該輪的工作副本移出「審閱中」或直接刪除 |

**第 4 步是整條流程的關鍵。** 走到這一步，`git diff` 就是審閱報告、PR 就是審閱紀錄，
不需要有人另外整理「這輪改了什麼」——那份整理本身就是會過期的第二份事實。

### 為什麼堅持繞回 git

2026-08-30 的農生補審抓到兩個發現：**農生是九學群裡唯一頓號歸零的**（其餘 13–99），
以及**倫理區塊只有三個學群有，生醫只有 2 列**。兩個都是跨全部 45 份的統計，
是用一行指令量出來的。如果那些內容散在九份 Sheet 裡，這兩個發現不會出現。

**內容在 repo 裡，才驗得動跨檔案的一致性。**

## 五、什麼時候可以建出貨用 Sheet

依 **D-013**，該批要同時滿足：

1. **批次審閱完成**
2. **說明書輪調完成**——輪調會回頭改 CSV，這不是假設

（原本第 3 項「§07a 核取方塊定案」已由 D-014 定成不做，因此不再是條件。）

**上市波次的日期不是觸發條件。** 波次到了但該批沒凍結，就是不建。

滿足之後：建 Sheet 進「工具銷售」→ `template-manifest.json` 該筆改
`delivery: "external"` 並填副本連結（結尾是 `/copy`，不是 `/edit`）→ 重跑 verify。

---

## 六、已知的坑

- **建了 Sheet 之後 CSV 又改了。** 目前沒有就地更新 Sheet 內容的能力，
  只能重建 → 換檔案 ID → 換副本連結 → 已發出去的連結指向舊版。
  這就是 D-013 要求先凍結的原因。根治要寫 Google Sheets API 的 sync script。
- **在 Drive 建的檔案 owner 是建立者，不是資料夾擁有者。** 放進「工具銷售」不會讓它變成
  TBD 帳號的檔案。出貨用的那批要用哪個帳號建，建之前要先確定。
- **副本連結貼成編輯連結。** 網址結尾必須是 `/copy`；貼 `/edit` 等於把正本交出去。
- **兩個人同時改同一份。** 輪調規則本來就一人一份，但跨輪次時要確認前一輪已經合併進 main。
- **審閱者看到的是舊版。** 入口是正式站，而正式站部署的是 `main`——工作還在 feature branch
  就等於他看到的不是最新的。發連結之前先確認該輪的改動已經合併並部署。
