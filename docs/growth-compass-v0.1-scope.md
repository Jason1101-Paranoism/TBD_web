# Growth Compass v0.1 — 模組取捨表

> 把 `positioning.md` 的定位套用到產品範圍。判準是三分法：
>
> - **🟢 觸發被看懂** — 軟體該做的核心。職責是「問出對的問題 + 給一口被看懂的感覺 + 把人交給顧問」。
> - **🟡 降級為顧問人工** — 看起來像軟體功能，但自動化會變「策略劇場」。v0.1 由顧問人工交付，軟體只呈現原料。
> - **🔵 Lucker 匯入 / 不自建** — 記錄層，外包。不重蓋輪子。
> - **🔴 砍掉 / 移出 v0.1** — 與定位衝突、或屬於太後期。
>
> 原始概念見專案根目錄的 Growth Compass 概念文。

## v0.1 收斂後的產品 = 三件事

1. **輕量自填**：使用者把經歷自填進來當原料（無 Lucker 匯入管道）；證明文件等敏感資料頭段不收。〔🔵〕
2. **反思捕捉**：對每筆經歷做敘事化捕捉——這是 TBD 的差異化資產。〔🟢〕
3. **觸發 + 交棒**：用質性相似案例 + 顧問人工解讀，給一口「被看懂」，把人導向初談。〔🟢→人〕

> 一句話：**v0.1 不是一個會給你雷達圖的測驗，是一個把你的經歷變成「可被顧問接手的敘事原料」、並讓你想找顧問的入口。**

### v1 最小切片（真正第一版，別一次做完）
共用主幹 ①–④ 就上線：快速捕捉（`origin`+`my_role`，＋「距離申請多久」當 lead 標籤）→ 被看懂（反射式+模板）→ 留 LINE → 質性案例推薦（手選、無百分比）。兩種模式的分歧體驗、Timeline、Narrative Graph、AI、顧問儀表板 UI 全部 v1 不做（儀表板先人工交付）。**最大風險是做太大。**

## 已定決策（2026-06）

1. **記錄原料來源 ＝ 輕量自填。** Lucker 無匯入 API/匯出管道，v0.1 由使用者輕量自填。欄位刻意做薄，定位仍是「敘事原料」而非記錄產品（不重做 Lucker）。

2. **專案歸屬 ＝ 頭段留官網側、後端 app 獨立。**
   - 第 0–1 階鉤子（無帳號、client-side、IG bio 可點）→ 靜態相容，留在官網 repo 或其旁的輕量頁。
   - 第 2–4 階（帶登入、Supabase）→ **獨立 repo + `app.tbd…` 子網域**。
   - 理由：同一 repo 會撞 output 模式（static vs SSR）、部署互相傳染風險、密鑰/PII 安全面擴大、CLAUDE.md 禁框架/後端、貢獻者心智不同、auth cookie/CORS 隔離。monorepo 雖正當但 ≠ 塞進現有靜態站，現階段不划算。

3. **未成年合規 ＝ 頭段先不收敏感資料。** 鉤子/首捕捉階段只收低敏感的敘事，**不收證明文件、不收身分資料**。家長同意 / 個資告知機制留到真正需要存敏感資料時再做（屆時仍為該功能的上線前置）。

4. **涵蓋低年級 ＝ 同引擎、兩種模式（導航 / 呈現），由「距離申請多久」路由。**
   - 第 1 階加一句輕問題「幾年級／距離申請多久」當路由訊號。
   - **導航模式**（高一二/大一二）出口＝留住（季節/里程碑觸發回來、看主線又長了什麼），下一步方向只用質性、由證據缺席推出，**不預測科系**。
   - **呈現模式**（高三/大三）出口＝交棒顧問（原樣）。
   - 理由：只服務高三會讓低年級「還沒要申請就關掉」，且長期飛輪需從低年級接住才轉得動。Timeline 與季節觸發因此對低年級「復活」（見取捨表）。

### 仍待處理（非阻擋 v0.1 啟動）
- 進到第 2 階要存使用者資料時，個資告知/同意的具體文案與流程。
- 若未來要收證明文件或開放未成年，需先補齊家長同意機制（可能需外部法律意見）。
