# TBD Growth Compass — 產品定位

> 競品分析後的定位結論。寫這份文件的目的只有一個：**避免之後在開發過程中，不知不覺把產品滑回「做另一個 Lucker」。**
>
> Status: 定位拍板（concept）
> 來源：2026-06 競品分析討論

---

## 一句話定位

> **TBD Compass 不是策略層，是「能問出對問題、並把人交到對的顧問手上」的策略層入口。**
>
> 記錄外包給 Lucker，判斷留給顧問，軟體只負責中間那一段「被看懂的觸發」。

---

## 為什麼不做記錄層

主要競品是 **Lucker**，它的護城河是：

```
學習歷程紀錄 + 高中市場 + 學校合作 + 既有用戶
```

這是「記錄層（Record Layer）」的護城河，由**學校通路**撐起來。如果 TBD 在「誰比較會記錄經歷」這條線上跟它比，就是送死——同一塊地還有 Notion、Google Docs。

**結論：不蓋記錄層。** TBD 站在記錄層的**上面**。

```
記錄      ← Lucker（我們不碰）
─────────────────────────
盤點 / 定位 / 主線 / 呈現   ← TBD（我們的位置）
```

理想關係：`Lucker → 匯入資料 → TBD Compass → 盤點與自我行銷`。
把自己定位成**消費 Lucker 輸出的上層**，比跟它搶記錄聰明。

---

## 回答的是不同問題

| | 回答的問題 | Value Proposition |
|---|---|---|
| **Lucker** | 我做過什麼？ | Record Yourself |
| **TBD Compass** | 我是誰？我適合什麼？我還缺什麼？我要怎麼呈現？ | Understand Yourself / Market Yourself / Build Your Personal Narrative |

一個高二學生可能在 Lucker 裡有 50 筆紀錄（科展、社團、志工、營隊），卻仍然不知道「我要申請什麼」。**TBD 補的就是這一段。**

---

## 真正的護城河是「人」，不是軟體

案例就是證據——TBD 賣的從來不是「幫你多做一件事」，而是顧問用判斷力做的重新詮釋：

- **田宓**：不是幫她參加活動，是幫她**重新理解自己的經歷**。
- **柏佑**：不是幫他增加競賽，是幫他**建立申請策略**。
- **宥榕**：不是幫他累積機械經歷，是幫他**把機械經歷講成一個故事**。

這三件事的共同點：**都是人做出來的判斷，不是演算法。**

所以軟體誠實的工作**不是「成為策略層」**，而是：
1. 把原料收乾淨，讓顧問能又快又便宜地做策略；
2. 給使用者剛好一口「被看懂」的感覺，讓他想要人的版本。

軟體交付「Understand Yourself」**只到「問出對的問題」為止**；「Market Yourself / Build Your Narrative」交給顧問。
這與既有定位句一致：**「CRM 幫你看見自己，顧問幫你呈現自己。」**

---

## 兩種死法（都要避開）

| 死法 | 長相 | 為什麼會死 |
|---|---|---|
| **做成另一個 Lucker** | 把產品做成經歷紀錄系統 | 記錄層是 Lucker / Notion / Docs 的地盤，沒有護城河 |
| **策略劇場（strategy theater）** | 自評問卷 → 雷達圖、案例匹配「81%」、自動產出「你缺成果整理」 | 長得像策略層，交付的卻是 Lucker 等級（甚至更差）的洞察。「我是誰／我適合什麼」這類問題**最不能用 Likert 問卷和相似度百分比回答** |

策略層是唯一的差異化戰場，所以**策略層做得淺 = 在唯一的戰場上輸**。假精確（百分比、自動缺口分析）不是扣分，是致命傷。

---

## 一個必須記住的反向風險

「自我探索 / Understand Yourself」這個**自助軟體**類別是一片墳場（StrengthsFinder、各種職涯測評、九型人格）——多數結局是「測完覺得有趣，然後沒有然後」。

死因一致：**沒接上高風險決策 + 沒有人接手後續。**

TBD 剛好兩個都有：升學/求職是高風險決策、顧問是接手的人。所以——
**別把軟體包裝成亮晶晶的 SaaS 來藏住顧問；要反過來，大方讓軟體當顧問的漏斗。命脈在人，不在那張雷達圖。**

---

## 差異化資產：反思 / 敘事，而不是記錄

Lucker 記的是「我做了什麼」；TBD 要的是「它對我意味著什麼、我學到什麼、它能接到哪條主線」。

**「反思」欄比較靠近策略層，而不是記錄層。** 因此 Vault 不該設計成記錄表單，而是**敘事素材的捕捉面**——這是真正屬於 TBD 的資產。（欄位與提問設計見 `growth-compass-reflection-design.md`。）

---

## 服務對象：從高一/大一就開始（兩種模式）

這個服務**不是「申請前健檢」，是一條長線**：從高一/大一接住人、陪著看見與累積，一路到申請時幫忙呈現。

**為什麼一定要涵蓋低年級**：你自己原始概念裡的「長期飛輪」（累積→盤點→匹配→缺口→自我行銷→升學→成功案例→回饋案例庫）**只有從低年級接住並長期留住才轉得起來**。一個只服務高三的產品，飛輪第一格就斷了；而且低年級才是更大的漏斗、更長的關係、未來案例庫的來源。

同一個核心引擎（看見／被看懂／主線），依「**距離申請多久**」分兩種模式，差別只在輸出方向與出口：

| | 累積／導航模式 | 呈現模式 |
|---|---|---|
| 對象 | 高一高二、大一大二（還有跑道） | 高三、大三（申請在即） |
| 核心問題 | 我正在長成什麼樣子？**下一步往哪走？** | 我有什麼？**怎麼把它講成故事？** |
| 出口 | **留住**（季節/里程碑觸發回來，陪伴累積） | **交棒顧問**（作品集/備審/面試，付費） |
| 賺什麼 | 信任、名單、長期關係、未來案例（錢遞延） | 立即轉付費 |

**護欄不變**：導航模式的「下一步」必須是**由證據缺席推出來的方向**（「你這條線只有想法、還沒對外成果」），而**不是**預測「你適合 OO 系」。仍然不做自動評分、科系預測、假精確缺口——是引導，不是判斷。

## 試金石與網路效應（定位守則）

**對外標語**：Growth Compass 幫你看見自己；TBD 幫你呈現自己。

**功能試金石（兩關都要過）**：(1) 幫使用者看見自己嗎？(2) 幫忙把原料交給顧問、或把人帶向顧問嗎？只過 (1) ＝ inert（無閉環）、只過 (2) ＝ extractive（無使用者價值）。

**網路效應的正確來源 ＝ 顧問養的案例圖譜，不是聚合學生資料**：每結一案，顧問替案例打主題標籤；案例庫越用越強 → 下一個學生越容易被看懂。這讓「人是護城河」成為會複利的資產，且避開未成年資料聚合的隱私風險。匹配「成長路徑」不匹配「某人 81%」（百分比已砍，不可借屍還魂）。屬 post-MVP 願景，v1 只在反思捕捉鋪軌（留主題標籤欄），詳見 overview / scope。
